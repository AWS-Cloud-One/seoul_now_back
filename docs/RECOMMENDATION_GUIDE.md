# GPT 장소 추천 실행과 알고리즘

## 무엇을 구현했나요?

`POST /api/v1/recommendations`에서 첫 추천, 추가 추천, 검색 조건 변경을 처리합니다.
GPT는 사용자의 말을 검색 조건으로 바꾸고 추천 설명에 넣을 근거를 선택합니다.
카카오가 실제 장소와 자동차 예상 이동시간을 제공하고, **서버가 최종 추천 순서**를 정합니다.
프론트 화면은 이번 작업에서 수정하지 않았습니다. Swagger `/docs`에서 API를 실행할 수 있습니다.

## 처음 실행하기

로컬 `.env`에 아래 항목을 입력하세요. 기존 DB 포트 등은 유지합니다.

```dotenv
APP_OPENAI_API_KEY=발급받은_OpenAI_API_키
APP_OPENAI_MODEL=gpt-4.1-mini
APP_KAKAO_REST_API_KEY=카카오_REST_API_키
```

기본 모델은 변경 가능합니다. 해당 OpenAI 계정에 모델 사용 권한과 API 사용 설정이 있어야 합니다.
설정 변경 후 프로젝트 폴더에서 실행합니다. 새 패키지는 필요하지 않습니다.

```powershell
docker compose up -d --build api
```

키가 비어 있으면 명확한 503 오류를 반환합니다. 키를 응답·로그·Git에 넣지 않습니다.
도시데이터·주차 데이터가 수집되지 않았거나 오래된 경우에도 장소 추천은 가능하며,
도로 혼잡도는 `확인 불가`, 주차는 `null`로 반환하고 ETA 기준을 사용합니다.
서울 데이터 수집 실행은 DATA_PIPELINE_GUIDE.md를 참고하세요. 추천 요청이 수집기를 시작하지 않습니다.

## API 사용 예

첫 요청:

```json
{
  "message": "시청역에서 차로 30분 안에 갈 파스타집",
  "conditions": {"origin_name": "시청역", "x": 126.978, "y": 37.5665}
}
```

위 좌표는 호출 형식 설명용입니다. 실제 앱에서는 사용자가 선택한 출발지 좌표를 넣습니다.
출발지 이름만 전달할 수도 있습니다. 이 경우 카카오에서 정확히 같은 이름의 결과가 한 곳이면
그 좌표를 사용하고, 모호하면 `needs_clarification`과 `origin_options`를 반환합니다.
선택한 출발지의 `x`, `y`를 conditions에 넣고 이전 응답의 state와 함께 다시 요청하세요.
GPT가 생성한 좌표는 받지 않습니다. 이동수단 입력 없이 항상 자동차 경로로 계산합니다.

추가 추천(응답의 state를 그대로 전달):

```json
{"message": "다른 곳 추천해줘", "state": "직전 응답의 state 문자열"}
```

검색어만 바꾸기:

```json
{"message": "고기 말고 파스타", "state": "직전 응답의 state 문자열"}
```

응답의 `recommendations`는 최대 3개이며 각 항목은 다음 정보를 포함합니다.

| 필드 | 의미 |
| --- | --- |
| place.id / name / x / y / address | 카카오 장소 ID, 이름, 경도, 위도, 주소 |
| place.place_url | 카카오가 제공한 장소 상세 페이지 URL. 미제공·유효하지 않은 URL은 null |
| duration_seconds | 실제 자동차 경로 조회에서 확인한 예상 이동시간(초) |
| traffic | 도착지 주변 도로의 소통 등급, 도로 ID, 원천 시각, 반경 |
| parking | 확인된 주차장 한 곳의 잔여 면수·거리·출처·원천 시각. 미확인은 null |
| explanation | 확인된 근거만 사용한 짧은 설명 |

`conditions`는 합쳐진 현재 조건, `state`는 다음 요청에 전달할 연속 검색 상태입니다.
`more_available`은 미노출 또는 추가 탐색 후보가 있다는 뜻이며 적합한 장소가 반드시 더 있다는 보장은 아닙니다.

| status | 다음 동작 |
| --- | --- |
| ok | 추천 표시, 원하면 추가 추천 |
| exhausted | 현재 검색의 남은 적합 후보 없음. 반환된 마지막 일부 후보는 표시 가능 |
| search_incomplete | 이번 요청의 탐색 한도 도달 또는 재확인할 후보가 남음. state로 계속 요청 |
| needs_clarification | 검색어·출발지 확인 또는 origin_options에서 선택 |


422는 조건·상태 오류, 502는 제공처 인증/응답 오류, 503은 미설정·한도·DB 오류,
504는 시간 초과입니다. 오류를 빈 추천 성공으로 바꾸지 않습니다.

## 추천 순서는 어떻게 결정하나요?

1. **후보 검색:** 검색어와 출발지 x/y, `sort=distance`, page=1, size=15로 카카오를 조회합니다.
   선택적 radius_m은 후보 탐색 반경입니다. 반경 안이라는 이유만으로 시간 조건을 통과하지 않습니다.
2. **시간 검증:** 후보마다 자동차 경로를 조회합니다. 실패한 후보와 제한 시간을 넘는 후보를 제외합니다.
   이동시간은 사용자가 지정한 값, 생략하면 기본 30분입니다.
3. **기본 정렬:** ETA가 짧은 순서로 정렬합니다. 최단 후보부터 180초 이내를 한 묶음으로 만듭니다.
   예를 들어 10분·13분은 한 묶음, 16분은 다음 묶음입니다. 13분과 16분이 가깝다고 묶음을 늘리지 않습니다.
4. **도로 비교:** 묶음 내 모든 후보의 정보가 확인되면 원활 → 서행 → 정체 순으로 비교합니다.
   후보 하나라도 도로 정보를 확인하지 못하면 그 묶음은 ETA 순서를 유지합니다.
5. **주차 비교:** 소통 등급도 같은 후보끼리, 모두 확인된 주차 근거가 있을 때 잔여 면수가 많은 순으로 비교합니다.
   미확인 주차는 0면으로 바꾸지 않고 ETA 순서를 유지합니다. 실제 0면은 확인된 값입니다.
6. **최대 3곳 선택:** 최종 순위대로 반환하고 카카오 장소 ID를 노출 이력에 기록합니다.

예: A가 20분·정체이고 B가 22분·원활이면 B를 먼저 추천합니다.
B가 24분이면 3분 범위 밖이므로 A가 먼저입니다. B의 혼잡도가 미확인이면 A가 먼저입니다.
이 알고리즘은 조회한 후보 안의 순서이며 서울 전체 장소를 전부 비교한 전역 최적 순위는 아닙니다.

정책은 `app/modules/recommendation/ranking.py`의 RecommendationPolicy에서 조정합니다.

## 혼잡도·주차 근거의 의미

- **도착지 주변 도로**: 장소에서 도로 선분까지 500m 이내인 서울 도시데이터 도로입니다.
  경로 전체나 행정동 전체 혼잡도를 뜻하지 않습니다.
- 원천 측정시각 기준 15분 이내만 사용합니다. 미래 시각, 시각 누락, 미인식 등급은 확인 불가입니다.
  수집시각으로 원천 시각을 대신하지 않습니다. 주변 유효 도로 중 가장 혼잡한 등급을 대표로 표시합니다.
- 500m와 15분은 프로젝트 정책이며 제공처의 실시간 보증이 아닙니다.
- 주차는 기존 ParkingRepository의 최신성·제공 표식·300/500/1000m 조회 정책을 재사용합니다.
  확인된 도시데이터 주차를 우선하고, 없을 때 시영주차장을 사용합니다.
  선택한 출처 내 잔여 면수가 가장 많은 주차장 한 곳을 근거로 사용하며 여러 출처 면수를 합하지 않습니다.
  도착 시점의 빈자리를 보장하지 않습니다.

## 추가 추천과 GPT 프롬프트

미노출 후보를 먼저 다시 경로 조회하고 근거를 갱신합니다. 적합한 후보가 3개 미만이고
`meta.is_end=false`일 때만 다음 페이지로 넘어갑니다. 같은 ID는 페이지 사이에서도 중복 제거합니다.
한 요청은 새 검색 최대 3페이지, 경로 최대 5개 동시 조회, 총 90초로 제한합니다.
카카오 페이지 상한은 45입니다. 시간·인증·한도 실패를 '후보가 없다'로 오인하지 않습니다.
조건이 바뀌면 페이지·미노출 후보·노출 이력을 초기화합니다. 변경 뒤에는 이전 검색의 장소가 다시 나올 수 있습니다.

전체 채팅 기록은 저장하지 않습니다. state는 조건·남은 후보·페이지·ID 이력을 담은
서명된 문자열이며 30분 뒤 만료됩니다. 암호화된 문자열은 아니므로 URL·공개 로그에 남기지 마세요.
항상 직전 응답 state를 사용하고 한 검색에서 요청을 순서대로 보내세요.
이전 state 재사용이나 병렬 요청 간의 중복까지 서버 DB 없이 보장하는 구조는 아닙니다.
기본 서명키는 프로세스마다 생성되므로 서버 재시작 시 상태가 무효화됩니다.
여러 worker/서버에서는 긴 무작위 `APP_RECOMMENDATION_STATE_SECRET`을 동일하게 설정해야 합니다.

- 해석: `app/modules/ai/prompts/interpretation.txt` — 신규/추가/변경과 명시한 변경 필드만 추출.
- 설명: `app/modules/ai/prompts/explanation.txt` — 확정 순서의 근거 키만 선택.
- 서버가 선택된 설명 문구에 검증된 숫자를 넣습니다. 자유 문장 생성으로 사실을 추가하지 않습니다.
  설명 호출 실패·ID 순서 변경·미확인 근거 선택 시 정형 설명으로 대체하고 explanation_source=template로 표시합니다.
- OpenAI Responses API에 strict JSON Schema와 store=false를 사용합니다. 이전 대화는 전송하지 않습니다.
  해석 요청에는 이번 메시지와 현재 조건, 설명 요청에는 확정 후보의 근거 문구를 전송합니다.

공식 참고: [OpenAI Structured Outputs](https://developers.openai.com/api/docs/guides/structured-outputs?api-mode=responses),
[GPT-4.1 mini](https://developers.openai.com/api/docs/models/gpt-4.1-mini),
[카카오 경로 결과 코드](https://developers.kakaomobility.com/guide/navi-api/reference.html).

혼잡도 미확인 ETA 정렬, 주차 비교·0면·오래된 값, 남은 후보 재사용, ID 중복 제거,
다음 페이지·소진·탐색 한도, 출발지 확인, 상태 변조·만료, 잘못된 모델·카카오 응답을 검사합니다.
기존 PostgreSQL/PostGIS 통합 테스트도 로컬 Docker DB에서 실행합니다.

```powershell

docker compose exec -T api ruff check app tests
docker compose exec -T api ruff format --check app tests
```
