## 목적과 기존 구조

사용자의 자연어 요청에서 변경 조건만 추출하고, 서버가 검증된 이동시간·도로 소통·주차 자료로 최대 3곳을 결정한다. 전체 채팅 기록이나 새 추천 DB 테이블은 추가하지 않는다.

루트 README, recommendation·ai·providers·prompts·clients·data_pipeline·tests·evals의 안내와 docs/API_CONTRACT.md를 확인했다. app/models에는 별도의 README가 없다. 실제 코드 기준으로 카카오 장소 검색과 자동차 경로, 도시데이터 도로 GeoJSON, 주변 주차장 조회가 구현되어 있다. POST /api/v1/chat/messages는 계약 문서의 예정 경로이며 실제 구현이나 기존 요청·응답 스키마는 없다.

## 접근 방식

- 가중치 합산은 이동시간과 도로·주차 점수의 교환 비율을 새로 정해야 하므로 사용하지 않는다.
- 사용자 요구대로 이동시간을 우선하고, 비슷한 시간 범위 안에서 도로 혼잡도와 주차를 순서대로 비교한다.
- AI가 후보를 검색하거나 순위를 정하는 방식은 사용하지 않는다. AI는 요청 해석과 확정 근거 설명을 맡는다.

## 요청 해석과 API

POST /api/v1/chat/messages에 message, 현재 conditions, 이전 응답의 state를 받는 명시적 스키마를 추가한다. 기존 지도·검색 API는 유지한다.

조건은 검색어, 출발지 이름·검증된 좌표, 이동수단, 최대 이동시간, 선택적 검색 반경이다. 최대 이동시간 기본값은 30분이다. 출발지 누락·모호함은 확인 필요 상태로 반환한다. 모델이 지어낸 좌표를 사용하지 않고 기존 장소 검색으로 출발지를 확인하거나 사용자가 선택한 좌표를 사용한다.

모델 출력은 request_type(new_recommendation / recommend_more / update_conditions)과 changes만 허용한다. 추가 필드, 잘못된 자료형·범위, recommend_more의 조건 변경은 검증에서 거부한다. update_conditions는 명시한 필드만 합치며, 누락된 필드로 기존 조건을 지우지 않는다. 페이지나 순위는 모델 출력에서 받지 않는다.

실제 제공처는 미정이다. README에 예정된 Bedrock을 연결하려면 모델 ID·리전이 필요하다. 대안은 제공처 주입 인터페이스·프롬프트·검증과 모의 테스트를 먼저 만들고, 미설정 상태의 실제 자연어 요청에는 명확한 미설정 오류를 반환하는 것이다. 키워드 규칙을 실제 모델 호출처럼 표시하지 않는다.

현재 경로 제공처는 자동차만 지원한다. 도보·대중교통 요청은 unsupported_transport로 반환하며 자동차 시간으로 대체하지 않는다. 다른 이동수단의 실제 지원은 해당 경로 제공처가 정해져야 한다.

## 후보 확보와 상태

카카오 검색은 query, x, y, sort=distance, page=1, size=15로 시작한다. radius는 탐색 범위일 뿐 이동시간 조건을 대신하지 않는다. 기존 카카오 통신 코드를 공통 클라이언트로 추출하여 기존 Router와 새 Service가 재사용하도록 한다.

각 장소의 경로를 조회하여 제한 이내 후보만 남긴다. 경로 없음·후보별 실패는 제외하며 인증·한도 등 제공처 전체 장애는 결과 소진과 구분한다. 요청 시간·동시 호출 수·한 요청에서 탐색하는 페이지 수에 상한을 둔다. 상한에 도달하면 아직 끝나지 않은 상태를 반환한다.

state에는 현재 조건, next_page, is_end, 미노출 장소 후보, shown_place_ids를 유지한다. 클라이언트가 전달한 ETA·혼잡도·주차 수치를 사실로 신뢰하지 않으며 상태 변조를 방지하거나 다시 검증한다. 추가 추천은 미노출 후보부터 재검증하고, 적합한 후보가 3개보다 적을 때만 다음 페이지를 추가한다. 후보 ID는 페이지 사이에서도 중복 제거한다.

조건이 실제로 바뀌면 페이지·후보·노출 이력을 새 검색으로 초기화한다. 이전 검색과 섞지 않는다. 후보 소진 시 exhausted, 아직 탐색 가능하면 more_available 상태를 구분하고, exhausted에서 검색어·범위 변경 안내를 반환한다. 전체 채팅 기록은 저장하지 않는다.

## 순위 세부 기준 — 구현 시 제안 기본값

1. 이동시간 오름차순, 동률은 장소 ID로 안정적으로 정렬한다.
2. 가장 빠른 미배치 후보를 기준으로 180초 이내 후보를 한 묶음으로 만든다. 다음 묶음도 같은 방식으로 만든다. 쌍별 비교만 사용하여 3분 차이가 연쇄적으로 넓어지는 문제를 피한다.
3. 자동차 묶음에서 비교 대상 모두에 유효한 도로 정보가 있으면 소통 등급으로 정렬한다. 누락 후보가 있는 묶음은 이동시간 순서를 유지한다.
4. 도로 정보는 도착지에서 도로 선분까지 500m 이내인 도시데이터 도로를 사용한다. 원천 측정시각이 현재부터 15분 이내이고 미래 시각이 아닌 자료만 사용한다. 수집시각을 측정시각으로 대체하지 않는다. 500m와 15분은 서비스의 제안 정책이며 공식 보증이 아니다.
5. 원천 소통 등급 원활·서행·정체를 사용한다. 주변 여러 도로의 대표값은 가장 혼잡한 유효 등급으로 하며 해당 도로 ID·시각을 근거로 보존한다. 속도에서 별도 등급을 만들어 내지 않는다. 누락·지연·미인식 등급은 확인 불가이다.
6. 같은 소통 등급 안에서 양쪽 모두 확인된 주변 주차 근거가 있으면 잔여 면수를 비교한다. 없으면 이동시간 기준을 유지한다. 비교가 비추이적으로 변하지 않도록 같은 등급 묶음 전체의 정보 충족 여부를 검사한다.
7. 주차는 ParkingRepository.nearby와 parking_availability를 재사용한다. 도시데이터 주차 출처를 우선하고 시영주차장은 보완 출처로 조회한다. 여러 제공처의 면수를 합산하지 않고 확인된 주변 주차장 한 곳의 잔여 면수와 거리·출처·시각을 함께 반환한다. 미확인과 실제 0면을 구분한다.

3분, 도로 반경, 도로 최신성 등은 한 정책 객체에서 조정할 수 있도록 둔다. 순위 함수는 HTTP·SQL·모델 호출 없이 고정 입력으로 검사할 수 있게 한다.

## 설명과 응답

응답에는 request_type, status, conditions, recommendations, state, 안내를 포함한다. 추천 항목에는 카카오 장소 ID, 이름·좌표, 검증된 ETA(초), 도착지 주변 도로 근거, 주차 근거가 들어간다.

설명 프롬프트는 서버가 정한 순서·ID·근거만 입력받는다. '도착지 주변 도로'라는 범위를 명시한다. 확인되지 않은 이동시간·잔여 면수·영업 여부·주차 보장을 생성하지 않는다. 모델의 설명은 순서·근거 참조를 검증하고, 실패하면 서버의 검증된 수치로 짧은 정형 설명을 만든다. 요청 해석 실패는 정형 설명 대체와 달리 성공한 추천으로 처리하지 않는다.

## 검증 계획

- 기존 진입점의 예정 경로 /api/v1/chat/messages에서 신규 → 추가 → 키워드 변경의 연속 요청 검사.
- 20분 정체와 22분 원활의 순서가 실제로 바뀌고, 시간 차이가 3분을 넘으면 유지되는지 검사.

- 실패한 경로, 초과 ETA, 조건 변경 초기화, 상태 변조·유효성 검사.
- 모델 구조화 출력 오류, 조건 유지, 기본 30분, 설명의 순서·수치 불일치 검사.
- 기존 API 회귀 테스트와 Ruff 실행. 실제 API·실제 모델 호출 여부는 모의 검증과 따로 기록.
